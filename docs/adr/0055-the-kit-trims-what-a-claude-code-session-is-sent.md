# ADR 0055: The kit trims what a Claude Code session is sent

Date: 2026-11-14.
Status: accepted. The owner signed the request `claude-session-trim` (requests/archive/claude-session-trim: R1 to R6, and its change spec) on 2026-11-14, after a GPT model reviewed it (#751).
Decided by: the owner, by the sign-off of the request on 2026-11-14 (requests/archive/claude-session-trim/origin/2026-11-14-signoff.md). The shape is kit-dev/architect's ruling for the owner, on the facts and the candidates below. developer-751 wrote it.

## Context

A Claude Code session of the kit runs on Claude Code's own system prompt and its full tool list. The kit adds its text beside that: the bot's `AGENTS.md` through the `CLAUDE.md` link, the start prompt as the first message, and the permission rules. A review of two architect sessions on 2026-11-14 found that much of Claude Code's text does nothing for a fleet session, that some of it pulls against the fleet's rules, and that some of it describes tools that the session does not have. #751 asks for one text that the kit builds, under three principles, as #751 states them: take out the parts of Claude Code's text that are not relevant to a fleet session, tool texts and built-in skills included; keep, largely, what Claude Code says about how to develop; and flag each disagreement between Claude Code's text and the kit's rules for the owner, settled in neither direction.

Probes of Claude Code 2.1.325 against a local stand-in for the API, with no call to Anthropic, gave the facts this record rests on. They are in the tech notes, section 2, "The system prompt and what each switch does". The part-by-part judgment of Claude Code's text quotes that text, so it stays out of this repo until the owner rules on it (#751, boundary).

## The candidates

- **X, the shape to try (#751).** One system text that the kit builds: the trimmed Claude Code text, then the common rules, then the charter, then the role. `AGENTS.md` is kept from loading, so nothing loads twice.
- **Y.** The trim of tools and built-in skills; a main text that the kit builds from Claude Code's own text with whole units cut (Part 1); the rules and the charter in `AGENTS.md` as today, with a few chosen rule units also in the system text; the role as the first message, which the kit's SessionStart hook gives again after a compaction.
- **Z.** The trimmed Claude Code text and all of the kit's own rule units in the system text; the user's fleet units and the charter in `AGENTS.md`.

In all three, the trim of tools and built-in skills is the same switches (section 2).

## Decision

The kit takes shape Y.

### 1. The order of the build

1. The trim of tools and built-in skills, with the kit's default cuts, the user's lists and what `obk health` says.
2. The role after a compaction, and the kit's new lines in its rule units (R4, exact words signed by the owner).
3. Part 1: the main text that the kit builds, the recipe and the fallback by unit.
4. The placement of rule units: the appended system text, `CLAUDE.md` as a built file, the hook's guard after a bare resume, and what `obk rules build` and `obk health` say.

### 2. The trim of tools and built-in skills

- A tool is cut by a `permissions.deny` entry with its name in the bot's `.claude/settings.json`. Claude Code then leaves the tool's text out of the request (checked). When the tool adds a paragraph of its own to the main text, the paragraph goes too (checked for Artifact). The entry is in the bot's file, not on the launch line, so Orca's bare resume keeps it. `--disallowedTools` does the same from the launch line, for a cut that is the session's own.
- A built-in skill is cut by `skillOverrides` with `"off"`, in the same file, as the kit already does for `auto-mode-setup` (#708).
- The Workflow tool and the `workflow-authoring` skill go together or stay together. Without the skill, Claude Code puts its text into the tool's description.
- `--disable-slash-commands` is not used: it also takes away the bot's own skills.
- An MCP server's tools: a deny of the server's name takes the tool names out; the server's own instructions stay. What removes the Chrome section and the claude.ai connectors is checked at night (section 10).

### 3. The role after a compaction

The kit's SessionStart hook already gives the start prompt again after a `/clear`. Today it does not do so after a compaction, so the role lives only in the summary, in the model's own words. The change: it sends the role on the source `compact` too. After a compaction the first message is gone from the context, and the hook fires once. So the role is in the context once (checked with a probe hook, for `/compact` and for an automatic compaction).

### 4. Part 1: the main text that the kit builds, with the trim

- **Whose text ships: none.** Every Claude Code transcript records the system prompt that the conversation runs on, as a list of sections, with the version and the model. The kit reads the newest record of the harness's own text from the bot's own transcripts, for the same version, model and memory folder. The Memory section names the memory folder, so a record made before a change of that folder (#752) is not used.
- **Only the harness's own text is a source.** Once the kit gives a session its text, that session's records hold the kit's text: Part 1 with units cut, and the appended units in the same list of sections (checked, app-both). Built from such a record, the kit would append the units twice, and could not give back a unit that a later `claude_keep` names. A record that the kit did not give is not proof of the harness's own text either: an older conversation may have run with a user's own `--append-system-prompt` or a replaced text. So a source must be known by its inputs. On the sources `startup` and `clear`, the kit's SessionStart hook reads the launch line (checked in both modes). It never notes on `resume`: a resumed conversation keeps its older recorded text, whatever the new launch line holds; nor on `compact`, which keeps the conversation. When the whole line, the prompt included, holds no system-text flag but the kit's own appended-text flag, if the bot has one, the hook notes the conversation as a source in the bot's main text folder (`<bots>.claude-text/<bot>/`). The first ` -- ` of a line may be inside an option's value, so it does not mark where the options end. The note keeps the model that the conversation must run on: at `startup`, the `model` of the hook's input, which is Claude Code's own word for the model the process started with; at `clear`, whose input names no model (checked, 2.1.325), the model that the launch line named, which the book keeps as `launched_model` beside the shape of the same launch. With no model on the line, a clear is not noted. The kit takes a noted record only when the model of its first request is the noted model, so a switch of model before that request (`/model`, then `/clear`) gives no source, and `obk health` names both models. The kit reads only the first record of a noted conversation, which the noted start or clear produced: a later resume with other flags, and a compaction after it, can record another text in the same conversation (checked for the snapshot), and takes out its last section when the kit appended one, after it checks that the section is the text it appended (the appended text is a section of its own, checked). It saves the original text that it reads in the bot's main text folder, by version and launch shape, and builds every later text from that copy. After a Claude Code update, no saved original fits the new version: the session runs on the harness's own main text, with the appended units, until a new conversation on the kit's line (a first start, or a clear) records that text. A resume records nothing, and a session that the kit only resumes records by a clear (`obk session clear`). With the appended section taken out, that record is the new original. The next start gets Part 1: at once in a new conversation, and in a resumed one after its next compaction or clear (the snapshot). `obk health` says so meanwhile.
- **The recipe names units by hash and by name.** A unit is a whole section of the record or one line in it (a bullet, or a paragraph of one line). The recipe holds the sha256 of each unit it cuts, a name with the prefix `text:`, the owner of the cut, and the models it applies to. It holds no words of Claude Code's text. The `text:` prefix keeps a unit name apart from every tool and skill name. A test holds that no recipe holds a phrase of Claude Code, and that no unit that guards safety is named.
- **The units.** The kit's own cuts: `text:ultrareview`, `text:product-channels`, `text:fast-mode`, `text:no-planning-documents` and `text:drop-old-cautions` (the last two are in the Fable model's text only). A user's cut that the recipe knows: `text:login-tip`. The night run N2 showed that `--no-chrome` removes the Chrome section, so that switch replaces a `text:chrome` unit. The paragraph that the Artifact tool adds goes with the tool by the launch shape below, so no `text:artifact` unit is needed: the original of a launch with the tool cut does not hold the paragraph (N6). The Fable model's identity paragraph stays.
- **The launch shape.** A saved original fits only a launch like the one it was recorded under: the same Claude Code version, the same launch words that do not change from one conversation to the next (the model, the effort, the approval, the extra arguments in either form, Remote Control and the memory folder), the same tool and skill cuts, and the same Claude Code settings files that the session reads (the bot's two, its repository's local one, and the user's or the Orca profile's), each by a sum without its `permissions.allow` and `permissions.ask` rules. These change the main text: a flag such as `--no-chrome`, a model's own paragraphs, a tool's paragraph. A `text:` cut or keep is not part of it, so a unit that a later keep names comes back from the same original. The kit writes the shape into the book at each launch, and the hook notes a source under it. A fenced probe on 2.1.325 gave the same main text and tools with one allow rule, three allow rules, an ask rule and a pattern deny rule as with none, so allow and ask rules, which `obk permission allow` and a person's answer to a prompt change most often, are left out; deny rules stay in, since a deny of a whole tool changes the text (N6). The settings' default `model`, which `/model` writes into the user's file, is left out for a session whose line names its model: a fenced probe on 2.1.325 with `--model` on the line gave the same main text with another default model and with none, and a control with no `--model` ran on the default model with another text. For a session that names no model it stays in. At each launch of the bot, saved originals of another version than the installed one go, and so do notes whose record is of another version or that have had no record for a week. Originals and notes of the installed version stay whatever their shape, so a temporary session of a role finds its role's original between two sessions. Since a new Claude Code version comes every day or two, the first start of each shape on a version runs on the harness's own text, and a temporary session that is that first start stays on it. `obk health` puts this normal wait on the session's line, which fails nothing; the cases that the user must act on (a record of another model, a version the kit cannot read, a recipe that cannot be read) stay findings. A session whose extra arguments carry its own `--settings`, in any form, gets no shape and runs on the harness's own main text: the shell can make the word name any file (a `~`, a wildcard, zsh's leading `=`), so the kit cannot tell what the setting gives (architect's ruling, PR #783). The kit names no memory folder for such a session either (#752), and `obk health` names both in the finding it gives for the session's own `--settings`. Cost: after a change of the shape, the session runs on Claude Code's own main text until a new conversation records it. Not in the shape: the account (`text:ultrareview` depends on it), the tab's environment, and a change of Claude Code's text with no new version; the user removes the bot's `originals/` and `sources/` folders after such a change, since a pending note would build the text again. The kit asks `claude --version` itself, so a tab that finds another `claude`, or a Claude Code that updated itself between that question and the start, can run on a text of another version.
- **The boundary marker.** The record holds a marker line between the static and the dynamic parts, which no request carries. The build always drops it. It is not a unit, and no list names it.
- **The fallback is by unit, with no version rule.** The kit cuts each named unit that it finds in the record, and leaves every unit that it does not find, named or not. So a new version gets the cuts that still match, and a changed or new unit stays in until the recipe names it, which is the safe direction. With no fitting record or no recipe, the session runs on the harness's own main text, and `obk health` says why. `obk health` names a recipe unit that it did not find in a record of a model that the recipe names it for, so a changed unit is seen. Seen on this machine: four Claude Code versions in eight days; a rule by exact version would leave the fleet on the harness's own text after most updates.
- **The text reaches the session** by `--system-prompt-file`, from a file in the bot's main text folder `<bots>.claude-text/<bot>/` beside the bots repo, never in the bots repo. No launch line names that folder, so a Codex session of the bot, whose sandbox may write the kit's prompts folder, cannot change a note, a saved original or a main file. The kit also keeps there its own copy of the bot's last appended text, and when the units cannot be built it writes the appended file again from that copy, never from the newest file in the prompts folder. Limit: a session that may write anywhere (Pi, `--dangerously-skip-permissions`, or a write that auto mode lets through) can change the folder, as it can change the user's own Claude Code files. With that flag the harness sends the file's text and does not edit it. The Artifact tool's paragraph goes with the tool by the launch shape, so the build needs no `text:artifact` unit. The snapshot stays on: it keeps the text through Orca's bare resume (checked). Part 1 changes only with a harness or kit upgrade or a change of the cut lists; it reaches a running session after a restart and the next compaction, and `obk health` names a session that still waits for it.
- **Guards for the names.** A tool name that the version does not have prints a warning, and the session starts (checked). A skill name that it does not have is ignored (checked). `obk health` names each name in a cut or keep list that the installed Claude Code or the recipe does not know, of any kind, so a renamed tool or a mistyped unit is seen.

### 5. Where a rule unit goes

- **Three placements, for every harness.** A rule unit may name its placement in its front matter: `all` (the default, and the value of a unit that names none) is in the instruction file only, as today; `main` is in the session's system text and not in its instruction file; `both` is in both, built from one source. Any other value is refused with a message, and the kit builds nothing for that bot.
- **The tests, in order.** (a) A subagent needs the unit to do its work right: `all`. (b) It allows or limits an act that the permission check judges: `all`. (c) It only shapes how the main session talks, waits or arranges its work: `main`. (d) It holds the owner's hard limits: `both`. A unit moves only when the test is clear. A subagent and the client-side permission check read `CLAUDE.md`, not the system text (checked).
- **The kit's placements.** `talk` and `profiles` are `main`; `limits` is `both`; every other kit unit, `review` included, is `all`. A user places the fleet's own units in their front matter.
- **On Claude Code.** The kit gives the `main` and `both` units by `--append-system-prompt-file`, whether or not Part 1 applies. Claude Code adds the appended text after its own main text, or after the text of `--system-prompt-file` (checked), so no session loses a `main` unit when Part 1 falls back. The settings keys for a system text in a project `.claude/settings.json` do nothing (checked), so the launch flag is the only road.
- **`CLAUDE.md` is a built file** in a Claude Code bot with a `main` unit: every unit but the `main` ones, built in the same step as `AGENTS.md`, at every bring-up, so the two cannot differ. Claude Code reads only `CLAUDE.md` when it is a real file beside `AGENTS.md` (checked). A hand edit of `CLAUDE.md` is shown as a conflict, as for `AGENTS.md`. A bot with no `main` unit keeps the link. This changes a promise of the PRD, section 6.6 (change spec, SP-16).
- **`AGENTS.md` holds every unit,** whatever the placement.

The costs, accepted:

1. `CLAUDE.md` is a second built file for a bot with a `main` unit.
2. **The "both" hazard.** After a change of a `main` or `both` unit, the file copy is new at the next `/clear` or compaction, but the system copy stays old until a restart and the next compaction: the system text is read once for each process, and the snapshot keeps the recorded text until a compaction (checked). So for a while a `both` unit can say two different things in one session. `both` is only for units that rarely change. `obk rules build` and `obk health` name each session whose system text is older than its bot's units. The README says this hazard where it tells a user how to place a unit, in the build issue of placement.
3. **Orca's bare resume** after a cold restore has no launch flag. With the snapshot on, the session keeps its recorded text, the `main` units included, until its next compaction or `/clear`. After either, it runs on the harness's own main text, and its `main` units are not in `CLAUDE.md` (checked in an interactive session, for both). The guard: the kit's SessionStart hook reads its parent process's launch line, which is the Claude Code process (checked in print mode and in an interactive session). On every source, `resume` included, the hook gives the `main` units as context, whatever the line says. It saw no flag on `resume`, `clear` and `compact` after a bare resume, and the flag after a launch with it (checked), but `ps` joins the words of the line with spaces: the same words inside another option's value, the bot's own system file path included, cannot be told from the flag (#776 review). So a `main` unit is in a main session twice, once in the system text and once as context; the kit's own `main` units are two files of 602 bytes together. A compaction that is the process's last request leaves no new record (checked), so the recorded text can be the harness's own; the context covers that too. The line's reading feeds only the book's note and `obk health`, which names a session whose line appends nothing; a line that hides the flag inside a value can make health miss that session, which still has its units. A kit restart ends the gap.
4. `obk health` names a session whose recorded system text is older than its built file, and a session that runs on the harness's own text, with the reason.
5. Codex and Pi: no cost in this record (section 7).
6. **A harness change** (`obk session change --harness`): at its next start the session is brought up on the new harness, and bring-up builds `AGENTS.md`, `CLAUDE.md` and the system text from the units. So the session gets every unit on its new harness.

### 6. What a user sets

- **On at the upgrade.** The kit's default cuts are on for every user from the kit upgrade that ships them. The release notes and the README say what the upgrade cuts and how to keep one. The kit gives no notice of its own at the upgrade. Cost: a tool that a user's bot relies on (a page through Artifact) is gone after the update until the user keeps it.
- **Two owners of the cut list.** A cut that rests on a kit unit, or on a thing that no session in a kit tab can use, is the kit's default: the Artifact tools, their skills `artifact-design`, `artifact-diagramming` and `artifact-capabilities`, and DesignSync (the kit's `limits`: publishing gets a yes), `update-config` and `fewer-permission-prompts` (the kit's `limits`: permission rules are the kit's to write), `init` (the kit builds `AGENTS.md`), `keybindings-help` and `plugin-authoring` (the terminal and the hooks are not the session's), and the five `text:` units of section 4. A cut that rests on a fleet unit of this user's is the user's.
- **One mechanism for the user's list and for each bot.** Candidates: (a) a list in `defaults.yaml` for every bot and in `bot.yaml` for one bot, as `rules` and `skills` are today, with a second list in `bot.yaml` that keeps one that the defaults cut; (b) a rule unit names the cuts that rest on it, in its front matter; (c) the session's `extra_args` with `--disallowedTools`, which exists today. (c) cannot keep what a default cuts and is written once per session. (b) ties each cut to its reason, but a cut that rests on no unit (a bot with no browser) has no home. Chosen: (a), as `claude_cut` in `defaults.yaml` and `bot.yaml`, and `claude_keep` in `bot.yaml` (R1 and R2). The same lists name tools, skills and `text:` units. A cut per role would need the same list on a `temp_roles` option; it is left out until the owner asks for it.
- **Use before a cut.** A cut goes on a list only after each bot's calls of the tool or skill in the last 30 days are counted from its transcripts, by names and counts only. A bot that used it keeps it, and its list says so. The counts for this fleet are in the design work, not here.
- Each of these is a new setting a user can use, so each is the owner's to sign.

### 7. Codex and Pi

The placement of a unit is the same for every harness. This record builds only the Claude Code side. Until the next issue builds the system text of Codex and Pi sessions, a Codex or Pi session gets every unit of its bot in `AGENTS.md`, as today: a `main` or `both` unit never leaves `AGENTS.md`. Pi 1.3.0 reads one context file for each folder, `AGENTS.md` before `CLAUDE.md`, so a Pi session never reads a unit twice (read in the installed code). Codex 0.169.0 reads `AGENTS.md` and not `CLAUDE.md` (read in the binary's strings; not run). Nothing here blocks their side: Codex `model_instructions_file` and `developer_instructions`, and Pi `--system-prompt` and `--append-system-prompt`, can later take the same placed units (read in their docs, not tested). A bot with sessions on two harnesses needs one `AGENTS.md`.

### 8. The memory folder (#752)

Part 1 depends on #752: a record names the memory folder that its conversation ran with, and today every bot shares one folder; #752 gives each bot its own, `<bot folder>/claude-memory`. So the record is chosen by version, model and memory folder (section 4). After #752 changes a bot's folder, the bot runs on the harness's own main text, with its appended units, until a conversation with the new folder is recorded.

### 9. The checks that a session still works

- Tests with fakes, by a separate author, with no Claude Code text in any fixture: the settings that the kit writes hold the cut names and keep every other entry; a recipe cuts only the units it names, found or not; an unknown unit stays; the boundary marker goes; no recipe holds a phrase; no record or no recipe gives the harness's own text, with the appended units still given; a record that holds a text the kit gave is never a source, and a unit that a later keep list names comes back from the saved original; only a record of a noted conversation is a source, with its appended section taken out, so an empty store after an update gets Part 1 at the next start; a record with a user's appended or replaced text is never a source; a conversation is noted on `startup` and `clear` only, never on `resume`; a noted start, then a resume with a user's text and a compaction before the kit first reads the source, still gives the first record; the hook gives the `main` units on every source with no appended text in the launch line; the text file is outside the bots repo; a unit with an unknown placement value is refused and nothing is built; a bot with no `main` unit keeps `CLAUDE.md` as a link.
- Two-harness tests: a bot with a Claude session and a Codex session, and a bot with a Claude session and a Pi session. `AGENTS.md` holds every unit; the Claude session's `CLAUDE.md` and system text hold each unit once, and a `both` unit twice. After a harness change, the next start gives the session every unit on its new harness.
- A fenced probe for each Claude Code version that the kit gets a recipe for: the request lacks the cut tools, skills and units; the appended units are there; the role is in the context once after `/compact` and after an automatic compaction; a bare resume keeps the cuts.
- One live run at night, on the architect's go word, in a throwaway bots folder: a session reads its mail, commits, uses its skills, keeps its role after `obk session compact`, and auto mode lets it do a step that its charter allows. This is the only check of how the model acts.

### 10. Night probes (each a live run: night, backup, notice, the architect's go word)

A real throwaway session shows the parts that only the account has, in its own transcript record, with no fake API: what `--no-chrome` removes; what removes the claude.ai connectors and their instructions (`--strict-mcp-config`, a deny of the server's name, a variable that the binary names); whether the Artifact skills go with the tool; and the `advisor` tool's text.

### 11. The build issues, after the owner signs

1. The tool and skill trim: the kit's default cuts, the user's lists, what `obk health` says, and the release notes and the README on the cut.
2. The role after a compaction, and the kit's new lines in its rule units.
3. Part 1: the record, the recipe with `text:` units, the fallback by unit.
4. The placement of rule units: the appended text, `CLAUDE.md` as a built file, the hook's guard, what `obk rules build` and `obk health` say, and the README on placement and the "both" hazard.

## Alternatives considered

- **X, the shape to try.** Not chosen: on the checked facts it saves about as much as Y (about 900 more in the fence, the cost of Y's two `both` units), and it needs four new mechanisms to get back what `AGENTS.md` gives today. Its rule changes need a restart of each session, and this fleet's rules change several times a day.
- **Z.** Not chosen: it has X's costs for the kit's units, and a bot with sessions on two harnesses would need two forms of `AGENTS.md`.
- **Y without Part 1 or placement.** It saves as much in the fence, but the main text keeps the units that pull against the fleet's rules, and every rule stays in a message.
- **A version rule for the recipe** (exact version, or the newest recipe for newer versions when every unit is found). Not chosen: with the fallback by unit, a new version keeps every cut that still matches, and a changed unit stays in.
- **Ship a trimmed copy of Claude Code's text in the package.** Not chosen: Anthropic's text in a public repo and package, stale with each harness version.
- **Capture the text by running the harness against a local stand-in for the API.** Not chosen: the transcript record gives the same text with no run.
- **The settings keys for a system text.** Not chosen: they do nothing in a project `.claude/settings.json` (checked).
- **Snapshot off.** Not chosen: Orca's bare resume then falls back to the harness's own text.
- **`--disable-slash-commands`.** Not chosen: it takes away the bot's own skills.
- **The guard only when the line appends nothing** (#776, round 2 of its review). Not chosen: the hook reads the line with `ps`, which joins its words, so a `--settings` value that names the flag and the bot's own system file made the hook give nothing, and the session lost its `main` units.
- **A launch marker for the guard**: an environment variable on the kit's launch line, which the hook inherits and Orca's bare resume does not carry. Not chosen: a new variable in the core that a user can also set.
- **Keep the line check and name the leftover case.** Not chosen: it leaves a way, small as it is, to lose a `main` unit.

## Consequences

- Good: each request is about 39% smaller (fence), and more on a real account. The text for tools a session does not use, and the units that pull against the fleet's rules, are out.
- Good: subagents, the permission check, Codex and Pi see every unit that they read today, except the `main` units, which only shape the main session. No word of Claude Code's text is in the repo or the package.
- Bad: the cut lists are new settings with two owners, and the placement is a new field of a rule unit.
- Bad: a `main` or `both` unit changes in a running session only after a restart and a compaction, and a `both` unit can say two things until then. `obk health` names such a session.
- Revisit if: a live run shows that a session follows rules better or worse from the system text; or Claude Code changes how it records the system text, loads `CLAUDE.md` or `AGENTS.md`, takes the appended text, or applies a deny to a tool's text.
  Confidence: high on what Claude Code sends, from the probes; not checked on how the model acts, which needs a real session.
